Verdict in 60 seconds

  • It is one tenant, not a template. lib/workspace-types.ts:4 sets tenantId='between-gigs' as a constant; the owner is a hard-coded email in lib/companies/types.ts:8; 7 tables have no tenant_id. The multi-tenant model exists only as types in lib/platform/contracts.ts, which nothing imports at runtime.
  • The repo is green, and already an archive. 175/175 tests pass in 12.9 s, tsc is clean, build takes 60 s. But ACTIVE_WORK.md declared GitHub retired on 2026-09-27; the live source is the Sites repo, and this snapshot lags it (release 3.65 synced, 3.66–3.69 already reserved).
  • Token governance is good; layout is fragile. One JSON token source with drift and contrast checks that fail the build. Against that: 30+ ad-hoc px breakpoints, 4,059 fixed px font sizes, 1,027 !important, a 7-file CSS patch stack, and nothing that targets 1920, 2560 or 3840.
  • Missing against the org standard: no i18n at all, no per-page actions registry, no WebMCP, no responsive matrix, no docs/README.md, prompts not stored verbatim. Tests cover data rules, not UI.
  • Worth carrying over as designs: the 12-capability actions contract in lib/tool-system (MCP + REST + CLI from one catalog), the module registry shape, the token pipeline, the relational wm_* schema, optimistic versions with append-only events, the auth pattern, and the fast test harness.
  • Recommendation: rebuild clean on the Company OS spine. Fork the Playset-LLC/company-os integration branch (Postgres 16 + Drizzle + Fastify 5, query and policy engine), add a Vite + React 19 + TypeScript strict shell, SpacetimeDB as the live surface in front of Postgres (Electric SQL as fallback), Yjs for text, shadcn primitives under a shell we own, the product as source of truth, git as a nightly export. Convex is dropped.
  • First steps: foundation on the company-os fork → shell geometry engine → document model, canvas and prompt box → component library and actions registry → hub bundle → import between-gigs, then Playset Company OS.
  • Five decisions are open (bottom of page), including which live layer sits in front of Postgres.

Core finding: tenancy

The app is a single-tenant hub with a portfolio catalogue bolted on.

  • lib/workspace-types.ts:4: export const tenantId='between-gigs';. Every workspace-store.ts query binds it. lib/journal/store.ts:4 repeats the constant.
  • lib/companies/types.ts:8: isPortfolioOwner() requires role==='super_admin', personId==='person-justin-massion' and email==='jmassion@gmail.com'. Line 9 hard-codes three companies (between-gigs, bienestar, lawfirm) to bespoke routes.
  • Company records live in the same workspace_records table under a second scope 'playset-portfolio', merged at read time with 30+ hard-coded seeds (WordPress, fal, Blender, WWE, Karol G, The White House). Seeds are research entries, not tenants.
  • Company-specific code paths: components/bienestar/*, lib/bienestar/*, components/lawfirm/*, lib/lawfirm/*, and lib/hardware/hub-cards.ts branching on company.id.
  • db/schema.ts: workspace_records, workspace_events and the 26 wm_* tables carry tenant_id; leads, form_responses, page_views, sketches, privacy_requests, welcome_email_outbox, sheets_connection do not.
  • 55 occurrences of 'between-gigs' as an id outside drafts; 334 occurrences of "Between Gigs" across 155 files. lib/tool-system/access.ts:10 grants tool permissions only when workspaceId==='between-gigs'.
  • The only template/tenant split is scope:'Template'|'Between Gigs' on module records, and the docs call it "navigation metadata, never an authorization policy".

Auth. Supabase email/password plus optional Google OAuth. Authorization is an active row in hub_memberships with the single role super_admin. Any super_admin sees the BG hub; only the hard-coded owner sees other companies. API and MCP accept a Supabase Bearer token with origin checks. The pattern is sound; the role model is one role.

Data. Two persistence models coexist: an EAV-style workspace_records(id, tenant_id, kind, payload JSON, version) plus append-only workspace_events with optimistic version checks, and a fully relational wm_* schema (projects, people, items, assignments, relations, messages, wiki revisions, time entries, shares, file versions, connections, external ids, delivery attempts, capacity, audit) added in migration 0011 with the comment "Additive; legacy workspace_records stay intact". Half-migrated by design.

State. React context per concern, heavy localStorage and sessionStorage, no global store library.

Recommendation

between-gigs is a single-tenant hub with a portfolio catalogue bolted on, not a multi-tenant template. The rebuild premise is right. Rebuild clean, one step at a time, and import from between-gigs rather than evolving it.

What to carry over (as designs, not files)

  • Keep The Company OS core (Playset-LLC/company-os, integration branch, not main): schema, query + policy engine with row policies AND-injected into every read, module manifests with install and additive field sync, atomic batch writes, and the 18 accepted ADRs. Start the rebuild from this branch.
  • Keep The actions contract in lib/tool-system: typed capabilities, dry-run, idempotent requestId, MCP + REST + CLI from one catalog. This becomes the per-page actions registry, the WebMCP surface and the voice vocabulary.
  • Keep The module registry shape in config/workspace-modules.ts (id, name, section, path, status, access, scope, dependencies), with nav derived from it.
  • Keep Token pipeline: one JSON token source, generated CSS, drift and contrast checks that fail the build. Keep the design-lock idea (snapshot + hash guard), drop the !important injection.
  • Keep The relational wm_* schema as the reference data model: tenant_id, revision, audit, shares with token hash, file versions with sha256, connections and external ids, delivery attempts with dedupe. That is the multiplayer-ready base.
  • Keep Optimistic-version records plus append-only events.
  • Keep Auth pattern: edge guard + server check + membership table, and Bearer tokens for agents. Replace the single super_admin role with real roles.
  • Keep Fast tests: node:test with in-memory SQLite, 175 tests in 13 seconds. Keep that speed bar.
  • Keep lib/platform/contracts.ts and docs/platform-foundation.md as the written brief for the tenant and release model.

What not to carry over

  • Drop Next.js file-based routing and the build-and-deploy loop. It is the structural reason "write directly onto the product" is impossible today.
  • Drop The hub CSS patch stack (7 layered files, 1,027 !important), 30+ ad-hoc pixel breakpoints, 4,059 fixed px font sizes, nothing above 1800px.
  • Drop Hard-coded tenant constant, owner-by-email checks, company-name branches in shared helpers.
  • Drop 69 archived draft routes, triplicated professionals funnel, four copies of the Terminal experience, 215 MB of media in git.
  • Drop The ultra-dense one-liner code style. It was agents saving tokens in source; it makes review and parallel editing painful and is why the ACTIVE_WORK reservation ledger had to exist.
  • Drop The release-per-commit ritual (186 releases in four days). Provenance should be captured by the system on every write, not by a hook that blocks commits.
  • Drop Company OS's throwaway React 18 dashboard and operator console, demo templates, per-client importers.

Stack recommendation

The product is the source of truth. Pages, components, actions, tokens, docs and data are records in a realtime database, rendered live. Git becomes a nightly export and disaster-recovery mirror, not the workflow.

  1. Runtime: React 19 + Vite + TypeScript, strict. No Next.js. Routes come from the module registry in the database, not from files.
  2. Realtime data: keep the Company OS spine. Postgres 16 + Drizzle + Fastify 5, with its metadata-driven tenant/entity/role/row-policy model and its query + policy engine (the strongest code in either repo). Realtime live surface (pages, components, presence, drafts, prompt box state): SpacetimeDB with TypeScript server modules and the React client SDK, in front of Company OS's Postgres, which stays the system of record for business data and row policies. Verified 2026-09-28: SpacetimeDB v2.10.1 (Sep 15, 2026), TypeScript/Rust/C# modules, React/Vue/Svelte/Next integrations. Not yet confirmed from its docs: row-level security for per-tenant reads and subscription query limits, which is why business data stays in Postgres for now. Electric SQL remains the fallback if SpacetimeDB disappoints. Yjs for collaborative text and code fields either way. Convex is dropped: it would mean rewriting a backend that already works.
  3. Auth: Company OS has a dev-stub auth with a clean seam for a real provider. Wire Clerk (its planned provider) or Supabase Auth through that seam in step 1. Roles per tenant: owner, admin, staff, customer, tester, viewer, plus dev mode as a flag.
  4. Components: shadcn primitives (Radix/Base UI) vendored as today, styled by our tokens. We do not use shadcn's dashboard blocks or its sidebar for the shell. The shell is ours.
  5. Styling: Tailwind 4 kept for utilities inside components, but no responsive utility classes in page markup. Layout responds through container queries and a shared size-class scale set by the shell.
  6. Collaboration: Yjs for text and code fields (already in the repo as Liveblocks/Yjs), Postgres records for everything else. Presence and cursors from day one.
  7. Code components: authored in the product, compiled in-browser with esbuild-wasm, stored as versioned records, sandboxed in an iframe until promoted. Custom code is the exception; most UI is composed from the library.
  8. Hosting: API on Fly.io or Railway (Fastify + Postgres, or managed Postgres such as Neon or Supabase), static shell on Cloudflare Pages. The ChatGPT Sites / Workers + D1 setup is retired with the old app.
  9. Models: a routing table, not prose. JEV for fast, cheap intents (screen control, tests, small edits, yes/no calls); Fable for judgment, architecture and shared code; Opus 5 for building modules and pages; Sonnet 5 for mechanical passes. The table is a record too, editable in the product.

The shell that never breaks

The shell is a small geometry engine, not a page layout. Five regions: top bar, bottom bar, left sidebar, right sidebar, stage. Each region declares a behaviour (hidden, collapsed, rail, full) per size class of the container, and the stage always gets the remainder.

  • Size classes come from the container width and a viewing-distance mode, not the viewport: phone, tablet, laptop, desk, wall (wall = TV / 10-foot, larger type and targets). Desk on a 4K monitor is a real mode.
  • Type and spacing are one fluid scale (clamp) per size class. No per-page pixel breakpoints, ever.
  • Regions never overlap the stage and never scroll the page; only the stage and sidebars scroll internally.
  • Every interactive element is at least 44px, focusable, and works without hover or drag. The shell enforces this by construction: the component library only exposes compliant primitives.
  • Invariants are testable: no horizontal overflow, no clipped text, targets ≥ 44px, focus order matches visual order, contrast passes. That is what makes the responsive simulator smart. It renders the same shell spec at 360, 390, 768, 1280, 1920, 2560 and 3840 and asserts the invariants instead of eyeballing screenshots. JEV can run it on every write.

The house dialect

Versus Finsweet Client-First and Tailwind. Client-First is a class-naming convention for Webflow (BEM-ish, utility prefixes, page-section wrappers). It is compatible with Tailwind in spirit but redundant in practice: Tailwind already is a dialect for CSS, and stacking naming conventions on it gives two vocabularies for one thing. Its real purpose is the part worth keeping: a shared, predictable vocabulary so any person or agent can read a layout and know what it does.

Our dialect sits above CSS and Tailwind and compiles down to tokens, container-query classes and component props. It is a typed schema with a plain-language text form, so it can be validated, diffed, spoken and edited from the prompt box. Three vocabularies:

  1. Shell regions: top bar, bottom bar, left sidebar, right sidebar, stage. Behaviours: hidden, collapsed, rail, full, floating.
  2. Geometry and responsiveness: size classes (phone, tablet, laptop, desk, wall); fit words (fills, hugs, wraps, stacks, sits beside, pins to top/bottom); spacing words (tight, cozy, roomy, airy); type words (whisper, body, heading, headline, billboard).
  3. Materials: flat, paper, glass, metal, glow, and later shader materials. A material is a token bundle (surface, edge, shadow, motion) that responds to size class and theme.

Example, plain form:

Left sidebar: rail on laptop, full on desk and wall, hidden on phone.
Stage: fills, roomy on wall.
Cards: paper, cozy.

That line compiles to the shell spec. A 10-year-old and an 80-year-old can read it, and so can JEV.

Parallel building without stepping on each other

  • Module boundaries are records with ids. An agent takes a lease on a module or page (visible as presence in the canvas), and its writes go to that agent's draft layer. Two agents editing the same text or code field merge via Yjs; two agents editing the same record resolve via optimistic version, with the router deciding. This replaces the ACTIVE_WORK.md ledger with something the database enforces.
  • Live build visibility: the canvas shows agent presence, a build feed of writes, and lets you watch a page assemble. That is the procedural feel.
  • Draft to publish per tenant: saved, preview, published, superseded, as in the ReleaseManifest type already sketched in contracts.ts. Publish is one action with permission.
  • Minimal safety: schema-validated writes, per-action permission, immutable history, and a publish gate. Nothing else stands between a prompt and the screen.

Docs and memory in the product

Prompts (verbatim), replies, decisions, changelog, kanban moves and page docs are records written in the same transaction as the work, and exported to the repo nightly as append-only numbered files. Memory is a first-class tenant resource (see the Caveman + Mem Palace note in the Slack thread): verbatim source plus summary, kind, tags, links, backlinks, embeddings, exposed over MCP.

Import path

Old repos and softwares become "sources" with an ingestion pipeline: pages → document model records with source_ref; data → tenant tables with source_ref and original ids; assets → object storage; docs, releases and memory → memory records. between-gigs is import number one: leads, form responses, wm_* work items, journal, releases and development-memory. The detailed import plan comes after the company-os read.

Order of operations

First steps only. The full dependency plan and the PM viewer come next.

  1. Foundation. Fork the company-os integration branch into the new repo, add the shell package (Vite + React 19 + TS strict), wire real auth through the existing seam, add a persisted audit/activity table, enforce row policies on the plain list route, add page versions (saved / preview / published).
  2. Shell geometry engine with the dialect schema, five regions, size classes, invariants test at seven widths.
  3. Document model + canvas + prompt box + router table. First live write to the product.
  4. Component library from shadcn primitives, materials, actions registry per page, WebMCP surface.
  5. Hub bundle: role switcher, dev mode, placeholders, EN/ES toggle, PM viewer (kanban, list, timeline).
  6. Import between-gigs data; then Playset Company OS.

Open decisions

1. Leave Next.js and the Sites / Cloudflare Workers setup, and build the shell as a Vite + React app on the Company OS API? Recommended: yes.
2. Live layer: SpacetimeDB (TypeScript modules + React) vs Electric SQL on Postgres. Recommended: SpacetimeDB. Going all-in on SpacetimeDB for business data is deferred until row-level security and subscription limits are confirmed.
3. shadcn primitives with our own shell, versus another primitives library (Base UI direct, Ark UI). Recommended: shadcn primitives.
4. Git as nightly export and mirror only, no PR workflow for product changes. Recommended: yes.
5. Name and home of the new repo, and whether docs start there today or wait for the product to host them. Open.
