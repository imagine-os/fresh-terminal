# 0015 — router deploy and the "no router" state

- The Pages site is static; POSTing to `/api/route` there returns HTTP 405. `app/src/lib/routerHealth.ts` decides first: `routerConfigured()` is true only for an absolute `VITE_ROUTER_URL` (or the dev proxy), then `probeRouter()` hits `GET /health` once per page load with a 3 s timeout and caches the verdict (`ok` with `keyConfigured`, or `unreachable` with a reason). The composer never POSTs when the router is not `ok`; it appends the system line with the inline K action instead. Own-key mode is unaffected (browser-direct).
- `.github/workflows/router-deploy.yml`: on push to `main` touching `terminal/router` or `terminal/shared`, a gate step checks the `CLOUDFLARE_API_TOKEN` secret (secrets are not available in job-level `if`, so the gate is a step output); when present it typechecks and tests the router, runs `wrangler@4 deploy` from `terminal/router`, then pushes `OPENROUTER_API_KEY`, `OPENAI_API_KEY`, `GOOGLE_API_KEY` from repository secrets into Worker secrets via `wrangler secret put` over stdin, skipping any that are unset. No key is ever written to the repo.
- CORS: `ALLOWED_ORIGINS` (comma list; `wrangler.toml` sets the Pages origin plus localhost 5173/4173 as the default) replaces the single `ROUTER_ALLOWED_ORIGIN`; unknown origins get no `access-control-allow-origin`.
- Pages: `VITE_ROUTER_URL` comes from the repository variable `ROUTER_URL` (the Worker URL, e.g. `https://fresh-terminal-router.<account>.workers.dev`). Until it is set the site shows the "no router" line and own-key mode works.
- What the owner adds once (Settings → Secrets and variables → Actions): secrets `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `OPENROUTER_API_KEY`, `OPENAI_API_KEY` (and `GOOGLE_API_KEY` when Gemini is wired); variable `ROUTER_URL`. Then re-run `router-deploy` and `pages`.
